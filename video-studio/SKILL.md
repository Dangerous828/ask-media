# video-studio

## 自看硬规则

任何产物出来都要自己看过才往下走：**视频一秒一帧，闸门过了不算看过。** 完整细则与"什么叫不算看过"见 [开发纪律](../ask-media/references/discipline.md)，本条不复述。

## 短剧项目协作（命中即读，保留本职）

本技能继续做工程检查、适配判断和问题定位，并提供测量（四件套、介质信号）。**短剧生成图片与视频是否可用，由 [short-drama-review](../drama-skills/skills/short-drama-review/SKILL.md) 的「媒体验收」裁决**：它用 `../drama-skills/skills/short-drama-review/scripts/look_check.py` 对照《视觉设定.md》「画风基准」先审画风，再审剧情；本技能的测量作为证据附上，不单独放行。涉及连续段时读 [short-drama-storyboard](../drama-skills/skills/short-drama-storyboard/SKILL.md) 的事件边界。规则见 [协作契约](../SHORT-DRAMA-ROUTING.md)。已读上下文复用；只有跨阶段、状态或初始化才读取short-drama主路由。

## 三、出图实验纪律（仅限 Qwen 静帧生图链路）

> **适用范围**：本节各条规则的证据全部来自本地 Qwen Image 2.1 静帧出图的小样本实验（角色C EP01 / 赛博题材）。
> 它们约束**生图提示词的槽位写法**，不约束剧本、分镜或 H3 视频提示词：不得据此否决夜景、黄昏戏，
> 不得为满足这些规则改写剧本时间设定。换画风或换后端时视为未验证，需重测。
> **现行口径**：风格词写在散文首行有效（剥离成前置锚词反而失效，证据见 `结论-提示词体系适用性.md` §二）；
> 「实体+发光色」词（金色粒子/蓝色光带/暖光/霓虹）允许——描述某个在发光的实体不是全局调色。

### R1b profile 的【规避】不进词流，只进拦截表

**本节记录 Qwen 静帧拼词实验：把【规避】清单拼入正向会引入被排除的概念——清单一入正向，模型就照着画。**
（实验当时与现行 Turbo 档同为 `cfg=1.0`、无独立负向分支，`--negative` 被渲染器静默丢弃。
**现行口径（2026-11-23 创作者确认）**：图片的负向通道仅 `cfg>1` 生效（档位现状以 MCP/h3qc 实读为准）；
cfg=1 档位无负向槽，【规避】只能以「拦截规则」存在于脚本/审查层。
无论哪个档位，【规避】都不能拼进正向词流。）
H3 的 negative 槽与正文否定须分开判断：单句否定与成串禁词的 H3 A/B 尚未完成，不能从该图像实验推断“所有 H3 正文否定都会反向生效”；见 [H3 剧本适配参考](references/craft/h3-script-fit.md) §5。

实测代价：我曾在 `build()` 里无条件追加【规避】（`死黑阴影`/`完全平面化`），
三轮 27 张图每一张都在要求模型画死黑阴影 —— 熵从旧 skill 的 6.92 掉到 6.41。

**规则：profile 的【规避】不参与拼接，只并进 `build_prompt.py` 的禁用词表。**
规避只能以「拦截规则」存在于脚本里，不能以「文本」存在于提示词里。

### R1c 五槽标签不进词流

`【景别机位】`/`【主体】`/`【画幅】` 这些标签是给写词人看的清单，**拼装时必须剥掉**。
`【画幅】` 整行丢弃——那是渲染参数，不是提示词。

官方 264 字散文效果好不是因为"散文"，是因为**零噪声 token**。

### R2 「可见光源」槽不许写暗

`【可见光源】` 必须指出**哪个实体在发光、照亮了什么**。
禁止 `暗` / `暗处` / `夜色` / `void` / `darkness` / `black` / `深蓝` 这类"没有东西"的描述。

实测：同一格只把后景从「夜色」改成「灯塔塔顶有光」，暗部从 78.0% 降到 67.3%（−10.7 pt）。

### R3 必须命名 1–3 个「会过曝的光源实体」+ 受光面

**不要靠「整个世界在发光」这类句式去救一个本身不发光的被摄体。** 对一个普通室内/人物场景，
写环境光弥散会让模型全局抬底噪，像素落进 16–50 带 —— 产出「均匀暗灰雾」而不是「被照亮的表面」。
但这不是句式禁令：当被摄体本身就是发光群体（整座灯塔城、成片灯火），这句是准确的描述，不是雾的成因。
**判据在被摄体，不在句式**——详见本节末尾「权威裁决」与 `结论-提示词体系适用性.md` §五。

#### 频带证据（本地复算，与外部复核逐位一致）

| 图 | <16 | **16–50** | 50–200 | **>200** | 熵 |
|---|---|---|---|---|---|
| 官方 ref_grid01 | 0.0 | **4.9** | 84.8 | **10.3** | 7.67 |
| 旧 skill sk_grid01 | 30.4 | 35.1 | 33.8 | 0.8 | 6.92 |
| 官方词裸跑 | 30.7 | 47.6 | 21.1 | 0.6 | 6.55 |
| 官方词+锚词 | 5.5 | 46.6 | 46.9 | 0.9 | 6.94 |
| 场景骨架 | 9.0 | 51.2 | 36.3 | 3.4 | 6.97 |
| **R3b 面光源** | **4.7** | **71.5** | 22.1 | 1.8 | 6.32 |

**本地每一张的 16–50 带都是 46–71%，官方只有 4.9%。高光带官方 10.3%，本地全部 ≤3.4%。**

`r3b` 是铁证：死黑 4.7% 已达标，但 16–50 飙到 71.5%、中间调 22.1%、熵 6.32 全组最低。
**它不是因为"面光源失败"，是因为那种写法制造了全组最严重的雾。**

#### 正确的写法：两个都要

| 要什么 | 提供什么 | 对应频带 |
|---|---|---|
| **高亮光源实体**（会过曝的那种） | 火、灯丝、太阳、屏幕、粒子、霓虹管 | **>200 高光** |
| **它们照亮的具体受光面** | 墙面、桌面、地面、脸的一侧 | **50–200 中间调** |

**只写受光面 → 得到 r3b 那种无高光的雾。只写发光体 → 高光有了但中间调空。**

官方提示词给的是**离散高亮物体**：
`golden particles` / `rivers of luminescent code` / `neon blue data streams`
—— 它们占 >200 带（官方 10.3%）。**有高光才有层次。**

#### 保留的规则

- **静帧槽位里少写抽象时间词**（夜/夜晚/夜色/深夜/黄昏）：Qwen 静帧单变量实验 −10.7pt。夜戏照拍，把“夜”写成具体发光实体（路灯、窗光、月光照在哪）；不适用 H3 视频正文。
- **不设「每个场景必须有『整个世界在发光』定义句」这条硬规则**。它对普通场景会制造 16–50 雾；但被摄体本身是发光群体时照写无误。两种写法的解释见下。

**权威裁决（2026-11-23；本条是「整个世界在发光」与五槽拼装的唯一口径）**：

| 说法 | 裁决 |
|---|---|
| 「整个世界在发光」该不该删 | **按被摄体决定，不按句式一刀切**：普通室内/人物场景删（防 16–50 雾）；灯塔城/灯海这类本身发光的被摄体保留（tB 用它拿到当时全集最好成绩）。`MEASURED-第五轮.md` §4.1 的「删错了」与 `MEASURED-第三轮.md` §七的「已删」分别指这两类场景，不矛盾。 |
| 五槽拼装 vs 散文 | 两者各有适用范围，不是谁取代谁：真实项目散文首行写法 21 张指标接近官方（`结论-提示词体系适用性.md` §一）；修掉两个 bug 后的五槽拼装产物 nx1_clean 四项全过（`MEASURED-第五轮.md` §3.1）。**选哪种按实测产物判定，不由本 skill 规定。** |
| 本 skill 定位 | 工具组 + 排障规律，不规定提示词正文（见本文件开头定位与 `结论-提示词体系适用性.md` §七）。 |

### R3b 环境密度：给「画面四边」分配光源实体，但不许写成弥散

**R3b 原版说「描述受光面，不描述发光体」——说反了一半。**

| 只写受光面 | 结果 |
|---|---|
| `左侧是一整面墙，被天花板隐藏灯带均匀打亮` | 死黑 4.7% 达标，但 16–50 达 71.5%、高光仅 1.8%（实测 r3b） |

**受光面给中间调，发光体给高光，两个都要。**

正确写法（四边各一个**实体**，不是"均匀打亮"）：

```
前景是桌面上一支点亮的蜡烛（火苗过曝），桌面被它照出一圈暖光；
中景是她与烛台，她朝向火的半张脸亮、另半张沉入阴影；
后景是书架，书架上方一盏射灯打亮顶层书脊；
左右墙面各有一扇开着的窗，窗外天光落在窗台与地面；
```

**关键差别**：
- `均匀打亮` / `整体照亮` / `光充满` → 环境光弥散 → 16–50 雾
- `烛火` / `射灯` / `窗外天光`（具体实体+会过曝） → 高光 + 中间调

### R3c 验收指标是四件套

**不要用 `gray<50` 当主指标。** 那个量纲在惩罚正常中间调——
Toonflow 原文要的是「亮暗过渡柔和、暗部不死黑」，对应的是**死黑**。

| 指标 | 定义 | 目标 | 作用 |
|---|---|---|---|
| **死黑** | `gray < 16` | ≤ 5% | 底部别塌 |
| **暗灰带** | `16 ≤ gray < 50` | **≤ 15%** | **防「暗灰雾」← 新增，最关键** |
| **中间调** | `50 ≤ gray < 200` | ≥ 60% | 主体有层次 |
| **高光** | `gray ≥ 200` | **5–12%** | **「被照亮」的度量 ← 新增** |
| 画幅 | 边长 32 倍数 | — | |

**熵不作门控。** 实测相关性：熵 vs 死黑 r=−0.836、熵 vs 亮度 r=+0.831、
熵 vs 中间调 r=+0.788 —— 它和明暗分布测的是**同一根轴**，不是独立护栏。
熵低不是因为"平"，是因为"暗"（像素堆在直方图底部，可取值少）。
`sk_grid09` 死黑 80.6% / 熵 5.00 就是这个机制。熵保留作记录。

```bash
# 档位必须显式给（无默认档：套错题材档会静默误判，实测同一批图默认档 1/9 vs 正确档 3/9）
python3 scripts/qc_image.py <图片或目录> --qc-profile cartoon3d

# 介质信号（四带查不出的那一半：粒子密度/体积光/噪点），相对基准、默认只告警
python3 scripts/qc_signals.py <图片或目录> --baseline <项目>/qc/baselines/cartoon3d/
```

**⚠️ 四带只测亮度分布，对「介质」完全盲。** 实测 example-project S09 四带两档全过、目检可用，
小亮块数只有官方参照的 1/5 —— 粒子/代码流/体积光这些**四带查不出来**，要用 `qc_signals.py`。
但介质信号**只能告警不能门控**：好/差两组区间重叠（官方 min=175 vs 差组 max=318），

### R3e 场景骨架：出图和出视频共用，但语言不同

`profiles/<画风>.md` 第七节的 20 条场景骨架（景别 + 空间特征 + 具体陈设 + 光源实体）
**不是只给生图用的**。

| 用途 | 怎么用 | 语言 |
|---|---|---|
| **出图**（Qwen 生图提示词） | 直接填进 `【环境密度】` 槽，中文 | 中文 |
| **出视频**（H3 提示词） | 翻译成英文，嵌进 `detailed_description` 的对应 `[Shot N]` 段 | **英文** |

官方 `base-en.txt` 对 `integrated_multimodal_description` 的要求是
「Describes visuals, actions, shots, speakers, dialogue, singing, and diegetic audio
along the timeline」——**画面/场景描写本来就是它的一部分**。

**但 H3 必须英文。** 中文骨架进 H3 前必须翻译，且要遵守：
- `[Shot 1]` 无时间戳，后续 `[Shot N] At MM:SS.mmm`
- 运镜写成自然英文（type / amplitude / speed）
- 对白用 `<d>[Language] ...</d>`，人声源给 `(S1)(S2)`

### R4 H3 提示词必须过官方结构

字段名、段序、时序记号一字不许改：

- 三段式（base）：`integrated_multimodal_description` → `overall_soundscape` → `non_diegetic_music`
- 六段式（Ref2VA）：`subject_definitions` → `summary` → `retention_analysis` → `detailed_description` → `overall_soundscape` → `non_diegetic_music`
- 时序：`[Shot 1]` 无时间戳；后续 `[Shot N] At MM:SS.mmm`，严格递增
- 参考标签：`<Picture N>` / `<Subject N>` / `<Video N>` / `<Audio N>`
- 四档保留标记：`fully_preserved` / `partially_preserved` / `attribute_transfer` / `weak_reference`

#### R4a FL2VA / L2VA 默认单段，分段等于点名切镜（实测）

官方 `references/official/base-en.txt:62` 的原文约束：

> FL2VA generally favors a **single shot** so the model can interpolate continuously
> from the first frame to the last frame. Use multiple shots only when they are
> **explicitly specified**.

官方 8 秒 FL2VA 范例（`base-en.txt:201`）里两张帧都标 `(from Shot 1)`，正文只有
`[Shot 1]` 一个段。**首尾帧同属一段，运镜与动作全在段内用连续语写。**

**本项目实测反证（必须记住）：** 把 FL2VA 提示词写成
`[Shot 1]/[Shot 2] At 00:01.200/[Shot 3] At 00:02.800` 三段式后，
H3 在帧 66（= 2.75 s，正好对上 `At 00:02.800`）产生**真硬切**：
相邻帧亮度差 106.5/255、直方图距离 0.64，机位与光照瞬时全换。
同一批里另外 5 段写成三段式但没触发，说明这是**概率性诱发**，不是稳定复现——
所以不能靠“这次没炸”当通过。

| 项 | 分段写法（错） | 单段写法（对） |
|---|---|---|
| 首尾帧归属 | `Picture 1 (from Shot 1)` / `Picture 2 (from Shot 2)` | 两张都写 `(from Shot 1)` |
| 正文章节 | 3 个 `[Shot N]` + 2 个绝对时间码 | 只有 `[Shot 1]`，无时间码 |
| 运镜 | 每个时间段一个机位状态 | 一个连续运镜贯穿全片（`in one continuous travelling move for the whole duration`） |
| 收尾 | 第 3 段描述终点 | 用 `decelerates into the exact spacing … of Picture 2 at the end of the shot` |

**历史记录（2026-10-22，含一次返工）：** 这个缺口曾经真实存在——`h3_lint.py` 对分段/单段都判 PASS，
A/B 两版同 PASS，真真切镜就这样漏过了闸门。现在 `check_fl2va_single_shot()` 已作为 **P0-4**
挂进检查列表：FL2VA 同时加载 Picture 1 与 Picture 2、出现 ≥2 个 `[Shot N]` 且正文没有硬切词 ⇒ 直接 P0 失败。
补测记录：改前 7 条 FAIL / 3 条 PASS，全部改单段后 **9/9 PASS**。

> **返工记录（同日复验时发现，勿再犯）：** P0-4 第一版用「首行有没有 `aligns with the … mark`
> 对齐句」来认 FL2VA。首行只要改写成 `Picture 1 is the first frame …` 这类等价措辞，
> **双帧三段式就整份漏过**（`h3_lint` 与 `h3_gate --strict` 双双 exit=0）——闸门又退回了
> 「只认我以为的写法」。现已改为**结构判据**：非 Ref2VA 模式 + 同时加载 Picture 1/2 = FL2VA。
> 同时 `h3-video-gate` 那边原先**根本没有**这条检查（三段式反而全绿），已补为 **G28**，
> 两条脚本现在同判据（均按 FL2VA 结构判据 + 同一份硬切声明词表）；它们是格式自检，不是内容放行条件。
> 「声明硬切 + 剧本事件清单里有对应 `transition` 事件」的白名单收紧仍是**待实现提案，尚未落地**
> （见 `MEASURED-Opus六信号复验.md` §五），不要当作已生效判据。

**判据要结构或相对，不要措辞或绝对阈值。** 同批踩过的坑：「首行有没有某个固定句式」漏判（上条）、
「全局 mad > 25」把连续升摇误判成切、「接缝绝对值」在慢镜与推轨里结论相反。
「首尾帧分属不同段」也只在**未声明硬切**时才算错——官方 `base-en.txt:62` 明确允许显式声明的多段。
**写检查器必须拿官方 `base-en.txt` 范例原文当测试集，不能拿自己生成的文本当测试集。**

仍保留人工复核：P0-4 / G28 只查「段数 vs 硬切词」，查不出「本该有切点却写成了连续」，那仍要人看片。

**只有真要硬切才分段**，且按官方 §4.2 用 `the camera cuts to`，并且
「只改景别或轻微角度优先用运镜，不要切」（`base-en.txt:92`）。

### R5 送 GPU 前双目检

任何出图/出片提交前，必须**逐张打开参考图本体**看：
画风与 profile 一致、是本镜第 0 秒起始态、图内文字无乱码、身份与角色锚点一致。

同一处连崩两次（同一只手、同一个人数不对），说明问题在提示词或参考图，不在随机性。

## 四、生产：怎么真出图 / 真出片

> **唯一提交入口是 h3q 队列（`h3qc.py` / 8200）。** 不要手调 `h3q_img.py` /
> `h3_quick.py` / `h3_render*.py` —— 它们直连 ComfyUI 8199，绕过 admission gate：
> 抢卡、不与队列互斥、看不到排队位次，也拿不到队列那道 VRAM 保护。
> `h3q_img.py` 自己的 docstring 就写着「never by hand; direct only to debug one still」。
>
> SSH 通道按 `h3-queue` §2 选择（同网段优先 `<渲染主机SSH别名-直连>`，远程走 `<渲染主机SSH别名-中转>` 等），以当时实测可连为准。
> 队列端口 8200 **只在 Windows 本机监听**，Mac 上查不到。

### 4.1 出图

```bash
# 在 Windows 上跑（h3qc 与队列同机）
# h3qc.py 为渲染机侧私有脚本，须另行部署（见 h3-queue §8）
python h3qc.py submit --kind image \
  --prompt-file p.txt --out <渲染机产物目录>\o.png \
  --size 1344x768 --seed 42 --label my-shot \
  --idem-key my-shot-s42 --wait
```

- 队列默认档位见 [h3-queue 档位实测](../h3-queue/references/still-standard-tier-20261105.md)，此处不复述数字
- **无负向通道**：排除项写进正文正向，不要用 `--negative`（会被静默丢弃）；
  `--fast` 仍被接受但被忽略。档位与回退配置详见 `h3-queue` §2.7 与上述档位实测文档
- **身份板、资产板**参考图压到长边 768 + JPEG q80（实测压后画面更干净）；**首帧、起始状态与构图参考**按目标画布无损 PNG 上传，不要压（short-drama adapter 已自动区分）
- **要挂参考图就走 `h3qg.py`**（= h3qc + 提交前闸门）：`python h3qg.py submit ...`
- **`--idem-key` 必须含 seed / 输出名**：同 prompt 换 seed 是不同活，
  只按 label 去重会让后续提交被静默吞掉（实测：12 张提交只渲出 4 张）

### 4.2 出视频

```bash
python h3qc.py submit --kind video \
  --prompt-file s1.txt --slug s1 --version v1 \
  --width 768 --height 1344 --seconds 10 \
  [--first-frame f.png | --refs a.png,b.png] --wait
# 示意为已有单帧/全参考模式；首尾配对、互斥输入和tier查h3-queue，短剧走produce adapter
```

当前输入、`draft/final/legacy` 与耗时依据统一查 [h3-queue](../h3-queue/SKILL.md#输入能力与续接职责)。本工具箱不缓存档位速查；final继承take须命中原latent，分辨率精修不能代替台词/口型验收。

**查队列**：`h3qc.py queue` / `health` / `ls` / `stats`（Windows 本机 127.0.0.1:8200）

### 4.3 帧数换算

H3 帧网格是 `17k + 5`（24 fps）：

| 秒 | 帧数 | 17k+5 |
|---|---|---|
| 2.5 | 60 | 56（短 4 帧）或 73（长 13 帧） |
| 3 | 72 | **73**（误差 +1，正好） |
| 15 | 360 | 362 |

**帧网格只约束本次任务的合法帧数，不决定镜头长度。** 先按事件、表演和生成分组确定任务时长，再选合法帧数并记录实际秒数；73 帧只是约 3.04 秒的换算示例。一个任务可含连续表演或有明确切点的多个镜头，成片入出点按实际素材选择。

### 排障：黑框在段内自溶

提示词层查不出来（EP01 里 S02 写「推镜穿屏」、S03 只写「满幅」，各自都对），
必须用帧级数据：

```bash
python3 scripts/segment_guard.py <成片段目录>       # 退出码 1 = 检出自溶
```

判据是**外环 6% 带死黑曲线的递减**（外环 drop ≥8% 且 下降帧远多于上升帧
且 只有环带在变）。两条硬规矩：

- **外环死黑「递增」不能拦** —— 那是合法的「边框被推入画」（推镜进屏幕）。
- **整帧同步变暗不能拦** —— 那是淡入淡出，不是局部自溶。

**它不能区分「非法自溶」与「合法地把黑框拉出画面」**（几何同形）。
创意上真要这么拍，用 `--allow-decay` 放行，并在项目文档写明理由。
