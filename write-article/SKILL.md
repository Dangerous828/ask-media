# 文章

## 目标

让读者读完能带走一个明确判断，并且相信这个判断有证据。文章的价值在主张的锋利与证据的具体，不在篇幅和辞藻。成稿要能直接投出去：标题、摘要、字数、来源清单齐全。


## 执行流程

1. 定中心主张、读者、文体、长度与投放（见下节四条）。
2. 取材：先读用户素材，再补查一手来源并记下 URL。
3. 搭提纲三到七节，标题写明这节讲什么。
4. 逐节写正文：主张、具体证据、这一节的代价或边界。
5. 改稿一轮解决一个问题，完稿过自检与 humanizer。用户问「像不像 AI 写的」「丢去审一下」时，走 humanizer 审稿模式，交独立体检报告，别把原稿贴给第三方检测器。

## 先定四件事

1. **中心主张**：一句能被反驳的话。写不出这句，这篇文章还没有方向。先跟用户确认这一句，别用三段"背景介绍"绕过。
2. **读者和他读完要能做什么**：决定术语密度、举例选哪个圈子、长度。
3. **文体**：不同文体的写法差异见下表，别把随笔写成周报。
4. **长度与投放**：1200 字和 6000 字的证据密度不同；公众号、博客、内部文档的排版约束不同。

| 文体 | 重点 | 别犯的 |
| --- | --- | --- |
| 观点随笔 | 主张 + 亲历证据 + 承认反例 | 升华结尾、"我们有理由相信" |
| 技术博客 | 问题场景 → 方案 → 可复现步骤 → 代价 | 功能清单式吹、"极致性能" |
| 复盘／周报 | 事实、数字、判断、下一步；失败写实 | 归因给外部、把结论写成口号 |
| 产品发布稿 | 用户得到什么、怎么用、限制在哪 | 形容词堆料、"革命性""重磅" |
| 行业分析 | 数据与出处、机制、你的推断单独标出 | 把推测写成事实 |


## 取材

有引用、数字、时间线、他人言论时先查再写：web_search 找一手来源，web_fetch 读原文，记下出处 URL。用户给的素材（笔记、聊天记录、旧稿、数据文件）先读，里面已有的事实优先于外部检索。

来源不足以满足某句断言时，把句子写弱到能撑住（"我们内部只统计到 Q2"），或者直接问用户要那个数。**不要用"业内人士表示""有研究发现"补位。**


## 结构

提纲三到七节，每节标题写明这节讲什么，不写效果（"三个失败原因"，不是"为什么值得重视"）。用户要的是小稿／单篇成稿时，给完提纲就继续写，不等批复；要系列或长稿时，提纲先过一轮。

开头三行决定留存。进场用：具体场景、一个反差事实、一个未解的问题、或直接给结论。禁止"在当今……的时代""随着……的发展""众所周知"开场；也禁止第一段复述标题。

正文每节：主张 → 支撑它的具体东西（数字、原话、时间地点、代码、截图描述）→ 这一节的代价或边界。段落 ≤3 行；一句一段只用在真需要转折或分量的地方，且那句必须带新信息。每节长度别一致。均匀段落是最容易被认出的机器形状。

证据密度按文体调整：技术稿每个关键结论配一个可验证的东西；随笔允许主观但要说清"这是我的判断"。

结尾落在最后一个具体事实、一个未解的问题、或读者能做的下一步。不总结全文，不升华，不"未来可期"，不"感谢阅读"，不加"关注我"式硬广（要引导就一句，放最后）。


## 公众号投放的硬约束

投放目标是公众号时，这几项直接决定点开率，成稿一并交付：

- 标题 ≤64 字，给 3–5 个候选，各带一句差异说明；避免点开率导向的虚假承诺。
- 摘要 ≤120 字，写清这篇给什么，不是复述标题。
- 封面 2.35:1（常用 900×383）；有配图需求时列需要几张什么内容的图与alt说明。
- 正文排版：段间空行、加粗只标真正需要跳读抓住的词（每屏至多一处）、小标题不加 emoji、分隔线不每节一条、外链在公众号正文不可点击（要放就写成文字＋读者可自行搜索的关键词，或放留言）。
- 图片版权与字体授权提醒用户，不由本预设承担发布动作。


## 调用契约

输入：一个主张或一段素材（笔记、旧稿、数据、会议结论），可选的读者与投放平台、长度要求、作者本人的文字样本。

输出：独立 Markdown 文件（不覆盖用户原稿；新建 `drafts/` 或按项目已有命名），用 present 交出，回复正文给四项：

1. 成稿或开头＋提纲（长稿别把全文灌进对话）
2. 标题候选 3–5 个 + 摘要（投放需要时）
3. 字数、事实来源清单（引用了哪些 URL／素材）
4. 你自己没把握、需要用户补的那条细节

不做什么：不替作者定立场、不编素材、不代发布、不为了凑字数灌背景段落；短内容转 write-tweet。


## 改稿

一轮集中解决一个主要问题（结构、事实、声音、长度任选其一），顺带的小改动可以捎上，别同时重写结构和语气。用户看不出哪处改动起了作用。改完重跑 humanizer 自检。

用户说"再人话一点""别太 AI"时，按 humanizer 的执行流程走完四步，不要只做同义词替换；同时保留上一稿里带他声音的具体细节、旁白和未解的感受，那些不是毛病。要只读判断而非改稿时，走 humanizer 审稿模式（独立报告，原稿不动）。


## 安全与权限边界

只写用户点名的项目与文件；引用他人文章、数据、图片要留出处，授权状态不明时先问。发布、排版、定时、多平台分发不在本技能内，按当前 Host 的通道执行，没有通道就交付文件与发布信息。涉及他人的评价、隐私、未公开数据时，写清来源与授权，不替作者承担法律责任。


## 自检

- 每句话给新东西了吗？删掉后文章变差了吗？没变差就删。
- 有没有原文没有的数字、日期、引语、出处？
- 破折号、三连排比、加粗标签、一句段收尾、升华结尾：按 humanizer 第 1/2/6/7/8/9 条扫。
- 段落长短是否一致得可疑？标题是否都在讲效果？
- 中心主张能否用一句被反驳的话复述；每节是否都在为它提供证据，而不是换个话题。
