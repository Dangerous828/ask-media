## Workflow

1. Read [references/summary.md](references/summary.md) for fit, input slots, and the concise starting example.
2. Read [references/template.md](references/template.md) completely before drafting.
3. Preserve the user's subject and objective, then fill every missing scene, trigger, event-chain, camera, sound, and payoff slot.
4. Treat these anchors as mandatory:

- Establish one stable user and the complete experience object together before the first trial.
- Show one independent close tactile, material or functional proof before relying on the user's reaction.
- Add a second proof that uses a different object component, scale or action.
- Repeat the opening user-object relation with a visibly changed terminal object state and a settled user.

5. Change source-specific people, setting, props, palette, dialogue, shot boundaries, sound family, and payoff surfaces together.
6. Compile MiniMax H3 and Seedance 2.0 independently; do not leak one model's field syntax into the other.
7. Silently verify anchor coverage, continuity, timing, physical causality, and anti-copy distance before returning the final prompts.

## MiniMax H3

- Use the current official H3 task grammar and language profile.
- Separate integrated visual action, overall soundscape, and non-diegetic music or explicit silence.
- Use timestamps only to make event order executable; keep shots consecutive and duration-safe.

## Seedance 2.0

- Define stable subjects once and preserve event order, camera motivation, sound intent, and overall duration.
- Use a simple paragraph for simple concepts or an ordered multi-shot structure for complex concepts.
- State overall duration once; do not copy H3 field labels or per-shot timecode grammar.

## Output

Return one concept sentence, the filled slots, an anchor-coverage check, one MiniMax H3 prompt, one Seedance 2.0 prompt, and a short anti-copy validation note.

## Non-Negotiable

- A subject-only request is underspecified. Preserve that subject and complete the mechanism instead of returning a generic portrait or showcase.
- Do not omit, reorder, or weaken a required anchor.
- Do not reuse source people, brands, dialogue, exact storyboard, signature props, exact timings, or recognizable effect surfaces.

# 感官体验｜对象建立—质感证明—试用反应—终态兑现 Template

## Mechanism

Establish one stable user and one complete experience object in the same frame. Before showing approval, isolate a tactile, material or functional close-up that visibly proves what the object does. Return to the same user for a complete first-use reaction chain, include one readable reset or relief action, then add a different detail for a second proof. End by repeating the opening relation with a clearly changed terminal object state and a settled user. The mechanism is objective proof to embodied reaction to terminal-state confirmation, not the source person, dish, market or exact food-vlog coverage.

## Invariants

### inv-01

- Rule: Establish one stable user and the complete experience object together before the first trial.
- Purpose: Defines who is testing what and provides an initial state.
- Failure if removed: Opening on a macro detail alone removes identity and completion context.

### inv-02

- Rule: Show one independent close tactile, material or functional proof before relying on the user's reaction.
- Purpose: Makes the claim inspectable rather than testimonial.
- Failure if removed: A reaction without object proof can feel staged or unsupported.

### inv-03

- Rule: Return to the same user for a complete first-use action, visible physical response and one reset or relief behavior.
- Purpose: Turns material evidence into embodied consequence.
- Failure if removed: Cutting away before the response or omitting the reset leaves the experience incomplete.

### inv-04

- Rule: Add a second proof that uses a different object component, scale or action.
- Purpose: Broadens the demonstration and prevents one-gimmick repetition.
- Failure if removed: Repeating the first insert at the same scale adds no new evidence.

### inv-05

- Rule: Repeat the opening user-object relation with a visibly changed terminal object state and a settled user.
- Purpose: Closes the test through before-after evidence.
- Failure if removed: Ending on a bite, hand or isolated smile does not prove what happened to the object.
